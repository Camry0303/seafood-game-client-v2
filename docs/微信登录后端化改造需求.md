# 微信登录后端化改造需求文档

> 适用范围：服务端仓库 `seafood-game-server-v2`（TypeScript 微服务后端）
> 关联客户端仓库：`seafood-game-client-v2`（Cocos Creator 客户端）
> 文档状态：需求评审稿
> 提出日期：2026-07-22

---

## 1. 背景与目标

当前客户端的微信登录流程中，**微信 `appSecret` 被写死在客户端代码**（`WeChatLoginService.ts`），并由客户端直接调用微信开放平台接口 `api.weixin.qq.com/sns/oauth2/access_token` 完成 `code → access_token/openid` 的换取。

该方案存在两个核心问题：

1. **密钥泄露风险**：`appSecret` 一旦进入客户端包体（apk/ipa），任何人都可通过反编译提取，等同于微信公众平台密钥对外暴露，可被冒用发起授权攻击。
2. **可维护性差**：更换 `appId`/`appSecret` 必须重新编译、重新打包发布客户端。

**目标**：将微信 `code → access_token/openid → 用户信息` 的换取逻辑全部迁移到服务端（`auth-service`），客户端只负责：
- 调起原生微信 SDK 拿到一次性 `accessCode`；
- 将 `accessCode` 传给服务端新接口；
- 拿到服务端返回的用户标识 / 登录 token，完成后续网关连接。

改造后客户端不再持有 `appSecret`，密钥仅存在于服务端配置/环境变量中。

## 2. 现状流程（改造前）

### 2.1 客户端调用链
文件：`assets/Scripts/Utils/WeChatLoginService.ts`

```
原生 SDK（Android/iOS）返回 accessCode
   ↓ NativeAPI.WeChatLoginAndroid() / WeChatLoginIOS()
   ↓ WeChatLoginService.doWechatLogin(accessCode)
   ├─ getAccessToken(accessCode)   ← 客户端用 appSecret 直连微信
   │     GET https://api.weixin.qq.com/sns/oauth2/access_token
   │         ?appid={appId}&secret={appSecret}&code={accessCode}&grant_type=authorization_code
   │     返回 { access_token, openid, refresh_token, expires_in }
   │     （expires_in >= 7200 时还会用 refresh_token 调 /sns/oauth2/refresh_token 刷新）
   ├─ getWeChatUser(access_token, openid)   ← 客户端直连微信
   │     GET https://api.weixin.qq.com/sns/userinfo?access_token={access_token}&openid={openid}
   │     返回 { openid, nickname, headimgurl, ... }
   └─ wechatAuthorize(userInfo)
         构造 Gateway.Requested.Authorization.WeChatAuthParams：
           openId, nickname, avatar(headimgurl),
           password = CryptoUtils.desEncryptPassword(
                         md5(openid).toString().slice(0, 8).toUpperCase()),
           time, sign
          POST {auth_server_url}:{auth_server_port}/wechat-authorize
          → 返回 { token }
          → 本地存储 token，SocketManager.Instance.connect() 连接网关
```

### 2.2 现有后端接口（保持不变）
文件：`assets/Scripts/Utils/HttpApiServices.ts`

```
POST {auth_server_url}:{auth_server_port}/wechat-authorize
请求体：WeChatAuthParams（已用 API_KEY 签名）
  {
    openId: string,
    nickname: string,
    avatar: string,
    password: string,        // = desEncryptPassword(md5(openId).slice(0,8).toUpperCase())
    time: number,
    sign: string
  }
响应：Result<{ token: string }>
```

> 即：后端 `auth-service` 已有「根据微信用户标识创建/匹配账号并签发 token」的能力（`/wechat-authorize`）。本次改造**不改动该能力**，仅把"获取微信用户标识"这一步从客户端上移到服务端。

## 3. 目标流程（改造后）

### 3.1 推荐方案（方案 B：服务端一站式）

新增一个服务端接口，由服务端持有 `appSecret` 完成全部微信交互，并复用现有账号匹配 + token 签发逻辑，直接向客户端返回 token。

```
原生 SDK 返回 accessCode
   ↓ WeChatLoginService.doWechatLogin(accessCode)
   ↓ 直接 POST 新接口 /wechat-login(code, sign)
       服务端（auth-service）：
         1. 用 appId + appSecret + code 调微信 /sns/oauth2/access_token
         2. （必要时）用 refresh_token 刷新
         3. 用 access_token + openid 调微信 /sns/userinfo 取用户信息
         4. 复用现有逻辑：派生 password、匹配/创建账号、签发 token
         5. 返回 { token, ...用户信息（可选） }
   ↓ 客户端拿到 token → 存储 → 连接网关
```

**优点**：客户端彻底移除所有微信 API 调用与 `appSecret`，代码最少、最安全。

### 3.2 备选方案（方案 A：仅上移换取，token 签发仍走现接口）

新增接口 `/wechat-exchange` 只负责 `code → 用户信息`，返回 `openId/nickname/avatar`；客户端仍用现有 `/wechat-authorize` 完成登录。

```
客户端 POST /wechat-exchange(code)
   ↓ 服务端换 token、取 userinfo，返回 { openId, nickname, avatar }
客户端用返回信息构造 WeChatAuthParams → 仍调现有 /wechat-authorize
```

**优点**：后端账号/token 逻辑零改动。**缺点**：客户端仍保留 `password` 派生、签名等逻辑，密码算法与服务端耦合，改密码算法需双端同步。

> 建议采用 **方案 B**。下文接口契约以方案 B 为准，方案 A 的接口为子集。

## 4. 接口契约（方案 B）

### 4.1 新增：`POST /wechat-login`

- **路径**：`/wechat-login`（与现有 `/wechat-authorize` 同服务、同端口）
- **鉴权**：建议沿用现有 `sign`/`time` 签名机制（用 `API_KEY`），防止接口被刷；`accessCode` 本身为一次性，泄露面小，但签名可防重放。

**请求体**
```json
{
  "code": "081abc...",          // 原生微信 SDK 返回的 accessCode
  "time": 1753000000,           // 秒级时间戳
  "sign": "a1b2c3..."           // genSignedParams({ code, time }, API_KEY)
}
```

**成功响应**（建议复用现有 `Result<T>` 结构）
```json
{
  "code": 0,                     // RESPONE_RESULT.SUCCESS
  "msg": "success",
  "data": {
    "token": "eyJhbGciOi...",    // 复用现有 token 签发逻辑
    "openId": "oMgfa6qWYJjJb5JRwBRU5ferYOkX",
    "nickname": "踏雪山巅",
    "avatar": "https://thirdwx.qlogo.cn/..."
  }
}
```

**失败响应**
```json
{
  "code": 10001,
  "msg": "微信授权失败：invalid code",
  "data": null
}
```

### 4.2 服务端内部需实现的微信交互（伪代码）

```ts
// 1. code 换 access_token
GET https://api.weixin.qq.com/sns/oauth2/access_token
    ?appid={APP_ID}&secret={APP_SECRET}&code={code}&grant_type=authorization_code
// 2. 必要时刷新（expires_in >= 7200 时）
GET https://api.weixin.qq.com/sns/oauth2/refresh_token
    ?appid={APP_ID}&grant_type=refresh_token&refresh_token={refresh_token}
// 3. 取用户信息
GET https://api.weixin.qq.com/sns/userinfo?access_token={at}&openid={openid}
```

- `APP_ID` / `APP_SECRET` 取自**服务端环境变量或密钥管理**，不得入库、不得下发客户端。
- 微信返回的 `errcode` 需映射到业务错误码并透出 `msg`。

### 4.3 密码派生（与服务端现有逻辑保持一致）

现有客户端密码算法：
```ts
password = desEncryptPassword(md5(openId).toString().slice(0, 8).toUpperCase())
```
方案 B 下该派生应在**服务端**完成（复用 `/wechat-authorize` 现有实现），客户端不再参与。

## 5. 客户端改造点（供客户端排期，非本次服务端范围）

文件：`assets/Scripts/Utils/WeChatLoginService.ts`

1. 删除 `getAccessToken()`、`getWeChatUser()` 中对 `api.weixin.qq.com` 的直接调用。
2. `doWechatLogin(accessCode)` 改为：
   - 构造 `{ code, time, sign }`；
   - 调新接口 `HttpApiServices.wechatLogin(code, sign)` → 拿到 `token`；
   - 存储 token，`SocketManager.Instance.connect()`。
3. 移除 `appSecret` 相关字段；`appId` 仅原生 SDK 注册需要（在原生工程配置，非 JS 层运行时变量），JS 层 `appId` getter 可一并清理。
4. 错误提示与 `WAITING_TYPE.WECHAT_AUTH` 加载态保持不变。

---

## 6. 服务端（auth-service）改造点

1. 新增 `/wechat-login` 路由（或等价 gRPC 方法经 gateway 暴露）。
2. 新增微信 HTTP 客户端封装：封装 `access_token` 换取、刷新、`userinfo` 获取，并统一处理 `errcode`。
3. 将 `APP_ID`/`APP_SECRET` 从硬编码改为配置项（环境变量 / 配置中心），**禁止写入代码或下发明文到客户端**。
4. 复用现有账号匹配 / 创建 / token 签发逻辑（当前 `/wechat-authorize` 的实现）。
5. 保留 `sign`/`time` 验签（与现有 `/wechat-authorize` 一致），防重放。

---

## 7. 安全收益

| 项 | 改造前 | 改造后 |
|---|---|---|
| `appSecret` 位置 | 客户端代码（可被反编译） | 仅服务端环境变量/配置 |
| 微信接口调用方 | 客户端（暴露流量特征） | 服务端（IP 可白名单/限流） |
| 换 `appId/appSecret` | 需重编译客户端 | 仅改服务端配置 |
| `appSecret` 泄露影响 | 可伪造授权、冒用 | 无客户端泄露面 |

---

## 8. 兼容与回滚

- **灰度建议**：新增 `/wechat-login` 与保留 `/wechat-authorize` 并存；客户端通过配置开关（如 `ServerConfig.use_backend_wechat_exchange`）决定走新接口还是旧流程，便于分批灰度与回滚。
- **回滚**：若新接口异常，客户端开关切回旧流程（旧流程依赖客户端 `appSecret`，需保留至全量切新成功后移除）。
- **注意**：旧流程依赖客户端 `appSecret` 这一事实本身即风险点，全量切新后应删除客户端 `appSecret` 相关代码。

---

## 9. 验收标准

1. 服务端 `/wechat-login` 仅凭 `code` 即可完成微信授权并返回有效 `token`。
2. 使用微信开发者工具 / 真机，走 `/wechat-login` 可正常登录并连接网关。
3. 搜包验证客户端安装包中**不含** `appSecret` 明文。
4. `APP_ID`/`APP_SECRET` 在服务端仅以配置项存在，日志中不打印明文。
5. 微信 `errcode`（如 `40029 invalid code`、`40163 code used`）能映射为清晰错误提示返回客户端。
